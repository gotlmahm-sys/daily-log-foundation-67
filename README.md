11. متطلبات التوسع للقوالب والبيانات

صمّم البنية بحيث يمكن لاحقًا إنشاء نظام Dynamic للبيانات والقوالب.

المهم جدًا:

لا تنشئ أعمدة ثابتة مثل:

قيام / عودة / فسحة / إجازة / مأمورية

داخل جدول السجلات.

أنواع البيانات والقوالب يجب أن تكون بيانات قابلة للإضافة مستقبلًا.

سيتم لاحقًا تنفيذ نظام يستطيع:

إضافة صيغة بيان.

إضافة موضوع.

إضافة متغيرات داخل البيان.

اختيار شخص واحد أو عدة أشخاص.

استخدام نفس الصيغة مرات متعددة.

حفظ الصيغ التي يكرر المستخدم استخدامها.

بالنسبة للكتابة اليدوية

المستخدم الذي لديه صلاحية الكتابة اليدوية يستطيع لاحقًا كتابة بيان غير موجود في القوالب.

يجب حفظ النص اليدوي كما كتبه المستخدم.

إذا تم استخدام صيغة يدوية بشكل متكرر، سيحتفظ النظام بها كصيغة قابلة لإعادة الاستخدام مستقبلًا، مع إزالة بيانات الشخص المتغيرة من الصيغة.

مثال:

كتب المستخدم:

قيام المجند أحمد محمد س 12 إلى المستشفى.

إذا تكررت هذه الصيغة، يحتفظ النظام بالنمط:

قيام المجند [الشخص] س [الرقم] إلى المستشفى.

ولا يحفظ “أحمد محمد” كجزء ثابت من الصيغة.

الصيغة المستخدمة نادرًا لا تختفي؛ تظل محفوظة ولكن تظهر في نهاية قائمة الاقتراحات/الصيغ الأقل استخدامًا.

والصيغ الأكثر استخدامًا تظهر في البداية.

يجب أن يكون ترتيب الاقتراحات ديناميكيًا حسب عدد مرات الاستخدام، مع إمكانية ترتيبها أيضًا حسب آخر استخدام في المراحل القادمة.

13. قيود التنفيذ

استخدم Supabase الحالي المرتبط بالمشروع.

لا تستخدم Lovable Cloud إذا كان المشروع يعتمد على Supabase خارجي.

لا تنشئ قاعدة بيانات ثانية.

لا تكرر أي جدول موجود.

لا تكسر أي وظيفة موجودة.

لا تغير منطقًا موجودًا إلا إذا كان ضروريًا لهذه المرحلة.

لا تبدأ تنفيذ Prompt 2.

لا تنفذ نظام القيام والعودة الآن.

لا تنفذ نظام التصاريح الآن.

لا تنفذ الإحصائيات الآن.

لا تنفذ Excel الآن.

هذه المرحلة هي Foundation + Authentication + Users + Permissions + Signatures + Basic UI.
